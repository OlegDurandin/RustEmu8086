# Индекс и аудит RustEmu8086

Дата: 2026-11-06. База: `1703187`, версия workspace `0.2.0`.
Проверены локальные исходники, README на двух языках, wiki, CLAUDE.md, TODO.md и workflows.
Это аудит реализации и воспроизводимости проверок; опубликованный сайт и GitHub Actions не проверялись.
Метод: инвентаризация всего дерева, выборочное чтение критических путей, сопоставление документации
с кодом и тестами, ограниченные воспроизводящие эксперименты. Полная формальная проверка CPU не проводилась.

## Вывод

Проект уже представляет собой учебную среду для двух архитектур: редактор, ассемблеры, машины,
обратимая отладка, устройства и три интерфейса. Главный следующий шаг — довести надёжность и
воспроизводимость учебного сценария «получил программу → запустил → понял результат».
Расширять совместимость стоит по потребностям конкретных уроков и программ.

Сильные стороны: отделённые от GUI ядра, архитектурная граница `Target`, общий слой сессии,
дифференциальные тесты против эталонных инструментов, обратимое исполнение и двуязычный справочник.
Главный риск: ограничения ресурсов введены по отдельности; часть путей MIPS и вычислений интерфейса
остаётся вне этих ограничений.

## Карта проекта

В `crates/`: 10 крейтов, 147 Rust-файлов, 63 303 строки с тестами и справочными данными;
394 вхождения `#[test]` (не число реально выполненных проверок).
В wiki — 40 Markdown-файлов. В `examples/` — 86 файлов `.asm`, включая два собственных NASM-примера;
в `examples/mips/` — 12 файлов `.s`.

Это разумная граница; сейчас приоритетнее укрепить её, чем добавлять третий процессор.

## Новые недостатки относительно списка TODO

Приоритеты соответствуют TODO: P1 — падение/зависание/вред системе, P2 — заметное нарушение работы,
P3 — улучшение. Статический вывод означает, что путь прочитан, но предельная нагрузка не запускалась.

### A1. P1: MIPS выделяет буфер чтения по недоверенному размеру

**Исправлено 2026-11-07 (MIPS):** чтение до 64 КиБ за вызов, запись до 16 МиБ; дескриптор, квота и диапазон источника проверяются до сборки буфера. Ниже сохранено описание исходного состояния.

`crates/rustemu-mips/src/syscall.rs:353` принимает положительный `$a2` для syscall 14 и передаёт его
в `Files::read`. В `files.rs:169` ветка `Storage::Host` делает `vec![0; len]` до чтения файла.
Даже для пустого файла запрос `0x7fffffff` требует буфер почти 2 ГиБ. Верхней границы или порционного
чтения здесь нет. Это статически подтверждённый путь к чрезмерному выделению памяти; запрос на 2 ГиБ
при аудите не выполнялся. Браузерная ветка чтения использует размер имеющихся данных и устроена иначе.

Действие: ограничить одну операцию ввода-вывода, проверять диапазон назначения, читать порциями;
обрабатывать исчерпание бюджета до выделения. Для syscall 15 также проверять размер и квоту до
сборки всего `Vec`: сейчас буфер создаётся до проверки `WRITE_QUOTA` в файловом слое.

### A2. P1: история MIPS копирует неограниченное состояние генераторов

**Исправлено 2026-11-07 (MIPS):** история хранит изменение одного генератора и потреблённые байты ввода; лимит 64 МиБ учитывает снимки и динамические данные, включая откат текста MMIO. До 4096 генераторов на машину. Упомянутый ниже аналогичный учёт состояния 8086 — отдельная задача. Ниже сохранено описание исходного состояния.

`syscall.rs:259`: потоки случайных чисел хранятся в `BTreeMap` по произвольному ID без ограничения.
`machine.rs:351`: перед каждым syscall `sys_state()` клонирует всю карту и очередь ввода.
`machine.rs:406`: предел 64 МиБ учитывает только журнал памяти, а не эти снимки.
Цикл syscall 40 с возрастающим `$a0` увеличивает и карту, и стоимость сохраняемой истории.
Даже syscall печати копирует уже накопленные генераторы. Статический вывод; предельный расход
памяти не измерялся.

Действие: журналировать изменение конкретного генератора, ограничить число потоков и учитывать
полный размер истории. Подобный учёт нужен и снимкам системного состояния 8086: его
`Snapshot::journal_bytes` считает журналы памяти и дискеты, а не весь `SystemSnapshot`.

### A3. P2: Last step выполняет квадратичную работу при отрисовке

`rustemu-session/src/step.rs:138`: для каждого изменённого байта выполняется линейный поиск
`writes.iter().any(...)`. Карточка планшета вызывает `Session::last_step` при отрисовке
(`rustemu-tablet/src/debugger.rs:101`). В MIPS-представлении повторён тот же алгоритм
(`rustemu-ui/src/mips_ui.rs:907`).

Изолированный замер **текущего исходника**, release, уникальные адреса в журнале:

| Изменённых байтов | Время `StepView::new` |
|---:|---:|
| 8 192 | 14 мс |
| 16 384 | 46 мс |
| 32 768 | 179 мс |
| 65 536 | 672 мс |
| 131 070 | 2 642 мс |

Большой `REP STOSW` даёт журнал сопоставимого размера. Замер относится к построению представления,
а не к длительности браузерного кадра; повторение этого вычисления в кадрах видно по коду.
Бюджет исполнения 12 мс в `App::tick_inner` не ограничивает построение карточки.

Действие: линейное накопление через таблицу адресов либо сортировка с удалением повторов,
кеш по номеру шага, ограниченный показ первых изменений с общим счётчиком.

### A4. P2: квота записи MIPS не ограничивает число созданных файлов

`rustemu-mips/src/files.rs:97`: `open(..., 1)` создаёт/обнуляет файл; после `close` дескриптор
снова доступен. Счётчика созданных файлов нет, а квота байтов изменяется только при записи.
Изолированная проверка создала **1100 пустых файлов в `Storage::Memory`** без ошибки.
Ветка хоста использует `OpenOptions::create(true)` и также не имеет общей квоты создания.
На диск пользователя массовое создание при аудите не выполнялось.

Действие: общий бюджет числа созданных файлов за запуск для обоих процессоров; в браузере
согласовать ограничения файлового слоя MIPS с 2 МиБ / 1024 записями `MemDrive` до изменения данных.

### A5. P2: лимит развёртки MIPS охватывает только макросы

`rustemu-mips/src/asm/mod.rs:646` проверяет `MAX_EXPANDED_LINES` в `expand`.
`include_lines` (`:1249`) добавляет обычные строки в вектор без общего счётчика байтов/строк;
входные файлы и их тексты также сохраняются. Проверка на 250001 строке комментариев и `nop`
успешно собрала программу за ~78 мс. Сам по себе этот пример не зависает: он подтверждает границу
действия лимита. Опасность больших входов следует из неограниченного накопления в потоке UI.

Действие: общий бюджет на исходник, включённые файлы, обычные строки и развёртки; число сообщений
ограничивать в ассемблере и отдельно в интерфейсе. Сборку сделать отменяемой.

### A6. P2: `--trace` выключает доставку `--keys` в CLI

`rustemu-cli/src/main.rs:270–309`: ввод MMIO-клавиш выполняется только в ветке без трассировки.
При одновременных `--trace --keys A` программа, ожидающая MMIO-клавишу, остаётся в ожидании,
хотя без трассировки получает её. Диагностическая опция меняет поведение программы.

Воспроизведено на текущей сборке с лимитом 100 инструкций: без trace — вывод `A`, код выхода 0;
с trace — `[instruction limit reached]`, код выхода 4. Программа:

```asm
.text
li $t0, 0xffff0000
wait: lw $t1, 0($t0)
andi $t1, $t1, 1
beqz $t1, wait
lw $a0, 4($t0)
li $v0, 11
syscall
li $v0, 10
syscall
```

Команды: `rustemu run probe.s --keys A --max 100` и та же команда с `--trace`.

Действие: доставлять MMIO-ввод до выбора режима исполнения; сравнивать результат одного сценария
с трассировкой и без неё.

### A7. P3: CLI молча принимает ошибочные параметры

`main.rs:66`: самописный `opt` не различает отсутствие значения и отсутствие опции.
`main.rs:258`: `--max nonsense` заменяется лимитом 100000000. Неверные значения `--org` также
подменяются умолчаниями; неизвестные опции не отклоняются централизованно.
Программа из A6 с `--keys A --max nonsense` действительно печатает `A` и возвращает 0.

Действие: типизированный разбор с ошибкой и ненулевым кодом выхода. Это важно для автопроверки
заданий, где опечатка должна быть видна сразу.

Дополнительные пробелы проверок:

- `emu8086_corpus::all_examples_run` допускает ожидание ввода, остановку и исчерпание бюджета;
  вывод печатается для просмотра, но не сравнивается с ожидаемым. Утверждение о запуске примеров

- PNG UI сохраняются без сравнения с эталонами; при недоступном WGPU рендер пропускается.

- Курс и внешний MIPS-корпус находятся в игнорируемых каталогах и пропускаются при отсутствии.

- CI проверяет wasm через clippy и собирает сайт, но не запускает браузерные сценарии загрузки,

- Нет `rust-version` и закреплённого toolchain: требование Rust 1.95+ находится в документации,
  CI использует плавающий stable. Стоит проверять заявленную минимальную версию отдельно.

## Подтверждённый существующий долг

Часть ограничений уже честно описана в TODO и wiki; это не новые ошибки аудита:

- Сборка идёт синхронно из UI; исполнение имеет бюджет кадра, но он проверяется между порциями,
  а не внутри каждой операции машины и интерфейса.
- Нет лимита числа сообщений; интерфейс обходит весь список. В MIPS привязка ошибки к строке
  дополнительно выполняет `split(...).nth(...)` для каждого сообщения.
- Ссылки не переносят настройки MARS; веб-ассемблер 8086 не использует пользовательский `MemDrive`
  для include, хотя MIPS его использует.
- Нет пакетного экспорта браузерных программ; хранение и квоты требуют отдельного развития.
- Last step доступен на планшете; на десктопе учебное объяснение шага не вынесено в аналогичную карточку.
- Пробелы совместимости: инструкции 80186 в ассемблере, STRUC/IRP/IRPC, часть видеорежимов;
  ограничения 8087 отдельно описаны в wiki. Закрывать их следует по проверяемым сценариям.
- Нет браузерной доступности через AccessKit; HTML запрещает масштабирование.
- Условия CI и загрузка trunk требуют укрепления; актуальность базы уязвимостей зависимостей
  в этом аудите не проверялась. Запись `cargo audit` от 2026-11-04 является исторической.

## Вектор развития и критерии готовности

### 1. Ближайший этап: предсказуемый запуск

Закрыть A1–A5, лимит сообщений и ввести единый `ResourceBudget` / отчёт использования ресурсов.
Для файлов, истории, исходников, вывода, устройств и генераторов определить владельца квоты,
единицу учёта и поведение при исчерпании. Тестировать оба процессора, историю on/off,
хранилище Host/Memory и UI-представления отдельно.

Готовность: превышение каждого лимита даёт контролируемую ошибку; большой REP не заставляет
карточку шага выполнять квадратичную работу; остановка и отмена сборки доступны пользователю.
Затем вынести сборку из UI: worker в браузере, фоновая задача на десктопе, номер версии документа
для отбрасывания устаревшего результата. Изолировать исполнение после измерений задержек.

### 2. Следующий этап: воспроизводимость программ и релизов

Исправить A6–A7, закрепить эталоны и разделить обычные проверки, дифференциальные и браузерные.
Сделать строгий режим CI, в котором отсутствие обязательных данных не считается успехом.
Добавить небольшой набор визуальных эталонов для обеих компоновок.

Разработать формат программы с версией: исходники + архитектура + диалект + настройки MARS + вход.
Использовать его для share, импорта/экспорта и заданий. Большие пакеты передавать файлом,
ограниченные — ссылкой. Проверять импорт с чистыми настройками и пустым хранилищем.

Готовность: одна программа даёт одинаковый результат в CLI, десктопе и браузере;
отчёт CI показывает, какие эталоны действительно запускались; отсутствующие данные видны явно.

### 3. Продуктовый этап: объяснение и проверка заданий

Общая карточка объяснения шага для десктопа и планшета; сравнение регистров/памяти до и после;
переход от изменения к исходной строке. На базе существующих тегов курса добавить задания:
вход → ожидаемый вывод/регистры/память → понятное объяснение расхождения.

Готовность: начинающий проходит несколько уроков 8086 и MIPS без переключения на внешние
инструменты проверки. Оценивать успешность прохождения уроков и понятность ошибок,
